# Adversarial review — ARCHITECTURE-SPINE.md (IMPOC Core)

**Date:** 2026-08-20
**Target:** `_bmad-output/planning-artifacts/architecture/architecture-IMPOC-2026-08-20/ARCHITECTURE-SPINE.md`
**Companion read:** `_bmad-output/specs/spec-impoc-core/domain-model.md`
**Method:** For each finding, two concrete units one level down (two epics, or two developers on adjacent features) that each obey **every** AD to the letter and still build something that will not compose. Nothing the spine gets right is restated.

Severity key — **Critical**: the two units produce contradictory rows or contradictory money and nothing in the schema catches it. **High**: divergence is caught late, at integration or on the dashboard. **Medium**: divergence is recoverable but costs rework. **Low**: cosmetic or one-line omission.

## CRITICAL

### C-1 — Rental day count: AD-7's inclusive `'[]'` bounds against the domain model's `endDate - startDate`

- **Two units:** *Epic Rentals / Booking (CAP-17)* — the developer computing `rent_charged_paise` and validating the maximum period at booking. *Epic Rentals / Settlement + Q11/Q12 (CAP-19, CAP-20)* — the developer computing overdue days and the read-side maximum period.
- **The AD they both obey:** AD-7 (`period daterange ... '[]'`, with the spine's own justification "a piece due back on the 17th is out on the 17th"), AD-16 (`maximum rental period is floor(deposit_paise / overdue_per_day_paise)`, `overdue is ... today > due_date`), and domain-model RentalBooking (`endDate - startDate may not exceed floor(deposit / overduePerDay) days`).
- **The concrete divergent outcome:** a booking `start_date = 2026-09-15`, `end_date = 2026-09-17`. The EXCLUDE constraint holds the unit for **three** shop days (15, 16, 17). The domain model's arithmetic yields **two** (`end - start = 2`). Booking developer charges `rent_per_day_paise × 2`; settlement/report developer renders "3 days out" on Q11 and prices the unit's utilisation on 3. A same-day walk-in (`start = end = today`) charges **zero rent** while the EXCLUDE holds the unit for a full day. The period cap is off by one in the customer's favour: with `deposit_paise = 500000`, `overdue_per_day_paise = 100000`, `floor = 5`, a booking of `start=1, end=6` passes (`6-1=5`) but is out for 6 days — one day of exposure beyond the deposit that AD-16's own "maximum rental period" formula exists to prevent. Overdue on the other side is consistent with inclusive bounds (`today - due_date`), so the same unit is billed on an exclusive count while it is out and an inclusive count once it is late.
- **The tightening:** add to AD-7 a named, binding definition: `rental_days = (end_date - start_date) + 1`, stated once as the only day-count expression in the system, and state that the period cap is `rental_days <= floor(deposit_paise / overdue_per_day_paise)` — i.e. `end_date - start_date <= floor(...) - 1`. Correct the domain-model RentalBooking line, which currently contradicts it. Add a `CHECK` on `rental_bookings` expressing the cap against the row's own `deposit_paise` / snapshot columns (see H-10 for which columns), so neither service can drift. Name the constraint `rental_bookings_period_cap_check` for AD-11.

### C-2 — `unit_status_events` has two plausible writers, and AD-8 only claims `units.status`

- **Two units:** *Epic Retail Checkout (CAP-14)* — the developer implementing `sales.service.js` from the AD-10 sequence diagram, which explicitly shows `sales.service → DB: INSERT unit_status_event` inside the sales transaction. *Epic Units (CAP-10, CAP-11)* — the developer implementing the AD-8 compare-and-swap guard in `units.service.js`, reading the Capability Map row "CAP-10, CAP-11 | `modules/units/` | AD-8 — the sole writer of `units.status`" and the domain-model line "the unit's `status` column is a cached projection of the latest event", and therefore writing the event inside the CAS helper so the projection can never diverge from its source.
- **The AD they both obey:** AD-8 (whose Rule is scoped to `units.status` only — it never names an owner for `unit_status_events`), AD-5 (which places `unit_status_events` in the append-only tier but assigns no writer), AD-10 (whose diagram shows the sales service inserting it).
- **The concrete divergent outcome:** both are built. Every retail checkout writes **two** `unit_status_events` rows for one `in_stock → sold` transition — one from `units.service`'s CAS helper carrying `sale_line_id = NULL`, one from `sales.service` carrying the real `sale_line_id`. `unit_status_events` is an AD-5 append-only table, so the duplicate can never be UPDATEd or soft-deleted away; only a reversing row, which the table has no reversal pointer for. AD-14 anchors shrinkage and forfeiture questions on `unit_status_events.occurred_at`, so every event-counted figure doubles. Conversely on the rentals hand-over path, the rentals developer — who read AD-8 as "units.service owns the whole transition" — writes **no** event at all with a `rental_agreement_id`, so the nullable FK to `rental_agreements` created in migration 17 is never populated and Q13's per-unit ledger has no rental history. The two paths cannot both be right and nothing in the schema rejects either.
- **The tightening:** make the CAS helper the sole writer of both columns and both tables. State in AD-8: "`units.service.js` exports one function `transitionUnit({ unitId, from, to, reason, actorUserId, saleLineId, rentalAgreementId }, { transaction })` which performs the CAS **and** the `unit_status_events` INSERT as one unit of work; every causal FK is passed in by the calling service; no other module INSERTs into `unit_status_events`." Then fix the AD-10 sequence diagram, which currently shows `sales.service` writing the event directly and is the source of the divergence. Add a partial unique index `unit_status_events_one_per_cause` on `(unit_id, to_status, sale_line_id)` / `(unit_id, to_status, rental_agreement_id)` so a duplicate is a `23505` rather than a silent double-count.

### C-3 — `v_rental_income` has no slot for `overdue_charged_paise`, and AD-13 forbids the workaround

- **Two units:** *Epic Reports / Q1 Takings (CAP-22)* — the developer building `reports/questions/q1.js` under AD-13's binding surface. *Epic Reports / Q12 Overdue (CAP-20)* — the developer building the overdue view, plus *Epic Rentals / Settlement*, which writes `rental_agreements.overdue_charged_paise` (domain model: "written once at settlement").
- **The AD they both obey:** AD-13 — "Three plain views are the **only** surface any money question reads. No takings, margin, or expense query may select from `sale_lines`, `expenses`, or `rental_bookings` directly", with the `v_rental_income` contract enumerating exactly three income kinds: rent, damage charges, forfeited deposits. AD-14, which gives no anchor row for overdue charges.
- **The concrete divergent outcome:** overdue money is real money — the shop charges `overdue_per_day_paise` per late day and collects it out of the deposit at settlement. It lands in `rental_agreements.overdue_charged_paise` and appears in **no** view. Q1 takings, built strictly to AD-13, under-reports the shop's income by every rupee of overdue ever collected. The Q12 developer, whose whole question is overdue, reports an accrued figure that reconciles against nothing. A third developer will eventually "fix" Q1 by joining `rental_agreements` directly — which AD-13's letter permits (the prohibition names only `sale_lines`, `expenses`, `rental_bookings`) while its spirit forbids, so the fix is both legal and a fourth surface. The same hole swallows `sales.exchange_difference_paise` (line-level views cannot express it without double-counting the netted lines) and `rental_agreements.deposit_returned_paise`.
- **The tightening:** extend the `v_rental_income` contract to a fourth `kind = 'overdue'` anchored to `returned_at`, and state explicitly that `overdue_charged_paise`, `damage_charged_paise` and forfeiture are the three settlement-time income kinds. Restate AD-13's prohibition as a positive whitelist — "a money question may read `v_net_sale_lines`, `v_net_expenses`, `v_rental_income`, and nothing else; `rental_agreements` and `sales` are as forbidden as `sale_lines`" — so the loophole closes. State that `exchange_difference_paise` is display/audit only and is never summed into a takings figure, because the netted lines already carry it.

### C-4 — A cancelled booking: the deposit refund exists in the drawer and in no row

- **Two units:** *Epic Rentals / Cancellation (CAP-17)* — the developer implementing "customer cancels, unit was never handed over". *Epic Reports / Q2 till reconciliation + Q6 deposits held (CAP-22)*.
- **The AD they both obey:** AD-5 (tier 2: `open → cancelled` is advancing toward terminal, so the UPDATE is legal, and the row freezes), AD-7 (the EXCLUDE predicate is `state IN ('open','handed_over')`, so cancelling correctly frees the dates), AD-13 (`v_rental_income` anchors rent to the booking's **creation** shop-day and says nothing about state), AD-14 (rent anchor = `rental_bookings.created_at`, "settlement moves no revenue").
- **The concrete divergent outcome, in four parts:**
  1. **The refund has no home.** `deposit_returned_paise` lives on `rental_agreements` (domain model), and a cancelled booking has **no agreement** — the agreement is created at hand-over. There is no column anywhere to record that ₹5,000 of deposit left the drawer. The cancellation developer's only options are (a) leave it unrecorded, so Q2's till never reconciles and the discrepancy looks like theft, or (b) INSERT a stub `rental_agreements` row with `handed_over_at = NULL` purely to hold `deposit_returned_paise` — which immediately collides with AD-9's `agreements_one_open_unit` (`UNIQUE (unit_id) WHERE returned_at IS NULL`) and permanently blocks that unit's next hand-over, or, if they set `returned_at`, silently creates a phantom settled rental in `v_rental_income`.
  2. **Rent on cancellation is undecided.** The domain model says rent is "not pro-rated for ... a cancellation, or a no-show" — which reads as *forfeited, keep it*. But `v_rental_income`'s contract anchors rent to creation day with no state filter. Builder A writes the view as `SELECT ... FROM rental_bookings` unfiltered (contract silent → include everything); Builder B filters `state <> 'cancelled'` (a cancelled booking obviously earned nothing). Both are defensible readings of the same one-line contract, and August revenue differs by every cancelled booking. Because the view is the *only* money surface, the divergence propagates to Q1, Q3, Q13, Q16, Q23 and Q24 identically and invisibly.
  3. **A no-show is a different case wearing the same state.** Booking made, paid, customer never appears. State goes `cancelled`. Rent forfeited — everyone agrees. Deposit: builder A returns it (nothing was damaged, nothing was taken); builder B forfeits it (the shop held the piece off the floor for the window). No AD decides, and the two answers differ by the largest single figure in a rental transaction.
  4. **Unit status is a no-op only by accident.** Because the spec bans a `reserved` status, cancelling a never-handed-over booking correctly touches no `units` row. That much composes — but only because booking never set anything, which is exactly the hole in H-1.
- **The tightening:** (a) add `cancelled_at TIMESTAMPTZ NULL`, `cancellation_reason VARCHAR NULL`, `rent_forfeited_paise BIGINT NULL` and `deposit_returned_paise BIGINT NULL` to `rental_bookings` itself, written exactly once as part of the `open → cancelled` advance, so the money movement lives on the row that holds the money. (b) State the policy in AD-5 or a new AD: on cancellation **rent is forfeited in full and deposit is returned in full**, and a no-show is a cancellation — one sentence, so both builders write the same rows. (c) Give `v_rental_income` an explicit state predicate in its contract: rent rows are emitted for `state IN ('open','handed_over','settled','cancelled')` because forfeited rent is still income, and a `kind = 'deposit_refund'` row (negative, anchored to `cancelled_at` or `returned_at`) so the till can reconcile. (d) Forbid a `rental_agreements` row without `handed_over_at`, as a `CHECK (handed_over_at IS NOT NULL)`.

### C-5 — The shop-day of a reversing sale line: AD-13's "so they cancel" and AD-14's anchor are mutually exclusive

- **Two units:** *Epic Reports / views (`v_net_sale_lines`)* — the developer writing migration 20. *Epic Reports / Q1, Q3, Q19* — the developers writing range questions on top of it.
- **The AD they both obey:** AD-13's `v_net_sale_lines` contract — "reversing lines carried as negatives, **reversed originals still present so they cancel**" — and AD-14's anchor table — "`sales` / `sale_lines` → `sale.sold_at` → The sale happened then", with half-open ranges on the shop day.
- **The concrete divergent outcome:** a sale on 30 September is exchanged on 3 October, inside the 7-day window. AD-10 says the exchange writes a reversing sale with its own row, and AD-14 anchors each line to *its own* sale's `sold_at`. Builder A implements it literally: the original line carries shop-day 30 Sep, the reversing line carries 3 Oct. September's takings are now **wrong and frozen** — the month closed showing revenue that was reversed, and the negative lands in October where no matching positive exists, so October shows negative revenue for a unit it never sold. AD-13's own sentence "so they cancel" is false for any range that does not contain both days, which is every monthly report. Builder B reads "so they cancel" as binding and anchors the reversing line to the **original** sale's shop-day — which makes the views correct and reconciling, and makes every closed period silently mutable: September's takings figure changes on 3 October, after the owner has already read it. Both builders are quoting the spine. The two `v_net_sale_lines` definitions differ by one `COALESCE` and produce different answers to CAP-22's own reconciliation criterion.
- **The tightening:** decide it in AD-14 and say why. The ledger-paradigm answer is Builder A's (a reversal is an event on the day it happened; closed periods never move), and it requires AD-13's contract sentence to be rewritten from "so they cancel" to "so they cancel **over any range containing both**, and a cross-period reversal is deliberately visible in both periods". Then add the consequence AD-13 currently hides: an exchange that crosses a month boundary makes September and October each individually non-reconciling against physical cash, and Q1 must expose a "reversals of prior periods" line so the owner can see it. If instead the shop wants closed periods to reconcile, state that the reversing line is anchored to `reverses_sale_line_id`'s sale day and accept that history mutates — but pick one, in the AD, by name.

## HIGH

### H-1 — A paid booking does not hold the unit against any other path

- **Two units:** *Epic Rentals / Booking (CAP-17)* — the developer who believes a paid booking holds the piece. *Epic Retail Checkout / Epic Units (CAP-14, CAP-10/11)* — the developer implementing the AD-8 CAS, who sees a unit whose status is `in_stock` and no reason to look further.
- **The AD they both obey:** AD-7 (whose EXCLUDE constraint is `EXCLUDE USING gist (unit_id WITH =, period WITH &&)` on `rental_bookings` **only** — it guards bookings against bookings and nothing else), AD-8 (whose CAS `WHERE id = :id AND status = :expectedFrom` sees `in_stock` and succeeds), and the spec's ban on a `reserved` status, which means booking deliberately leaves `units.status` untouched.
- **The concrete divergent outcome:** a customer pays rent and deposit on 1 September for a saree booked 15–17 September. On 5 September the unit is still `in_stock`, so the retail path sells it (`in_stock → sold`), or a CAP-11 channel conversion flips it to retail, or a damage grade sends it `in_stock → maintenance`, or it is retired. Every one of those is a legal AD-8 transition and none of them consults `rental_bookings`. On 15 September the hand-over CAS runs `WHERE status = 'in_stock'`, returns zero rows, and throws a 409 at a customer holding a paid receipt. AD-7's EXCLUDE — the spine's flagship guard — was never involved, because the competing write was not a booking. There is also no defined `expectedFrom` for the hand-over CAS anywhere in the spine, so the rentals developer must invent it.
- **The tightening:** state the hand-over transition explicitly in AD-8's table-driven guard (`(rental, in_stock, rented)`), and add the missing half of the hold: the `units.service` guard must refuse any transition **out of** `in_stock` other than `→ rented` when an `open` booking exists for that unit with `end_date >= (now() AT TIME ZONE 'Asia/Kolkata')::date` — one indexed predicate against the GiST index AD-7 already builds, inside the same transaction. Name it as a rule in AD-8, not as rentals-module etiquette, because the module that must obey it is `sales` and `units`.

### H-2 — "Deposits held" (Q6) has two legal definitions that differ by every un-collected booking

- **Two units:** *Epic Reports / Q6 (deposits held)* and *Epic Reports / Q2 (till reconciliation)*.
- **The AD they both obey:** AD-13 — "Deposits *held* are deliberately absent [from `v_rental_income`] — they are a liability and are queried separately for Q6" — and AD-14, which marks Q6 point-in-time and gives it no anchor and no source table.
- **The concrete divergent outcome:** Builder A computes `Σ rental_bookings.deposit_paise WHERE state IN ('open','handed_over') AND deleted_at IS NULL`. Builder B computes `Σ rental_agreements.deposit_paise WHERE returned_at IS NULL AND deleted_at IS NULL` — which is the exact predicate AD-9 already indexes, so it looks like the intended one. The two disagree by the deposit on every booking that is paid but not yet collected, which for a shop taking bookings a week ahead is most of the liability. Both are "the deposits we are holding". Because deposits are collected at booking (domain model: "Both collected at booking"), Builder A is right and Builder B under-states the shop's liability — but nothing says so, and Q2 will be built against whichever one its author read first.
- **The tightening:** name the source in AD-13's Q6 sentence: "deposits held is `rental_bookings.deposit_paise` summed over `state IN ('open','handed_over')`, because deposits are collected at booking, minus `rental_agreements.deposit_returned_paise` for agreements settled — `rental_agreements.deposit_paise` is a snapshot for settlement arithmetic and is never summed as a liability." Add `rental_bookings(state) WHERE deleted_at IS NULL` to the AD-15 index set.

### H-3 — `customers` has two writers and no named owner of the consent rule

- **Two units:** *Epic Customers (CAP-13, CAP-24)* — building `modules/customers/` with capture, lookup and erasure. *Epic Retail Checkout (CAP-14)* — where the customer is actually captured for the first time, at the counter, mid-cart, and *Epic Rentals / Booking*, which captures the same way.
- **The AD they both obey:** AD-18 (which governs erasure and reads, and names `customers.service` for neither create nor update), the dependency rule "a service may call another module's service" (so `sales.service` calling `customers.service` is legal, and `sales.service` INSERTing into `customers` itself is not forbidden by anything), AD-10 (one transaction per gesture — so the customer INSERT is inside the checkout transaction), and the domain model's "`consentGivenAt` ... Null is not a valid state for a customer attached to a transaction", which names no enforcer.
- **The concrete divergent outcome:** the customers developer enforces consent at create — `consent_given_at` and `consent_purpose` required, 400 without them. The checkout developer, needing to not block a walk-in, INSERTs a minimal `customers` row inline with `consent_given_at = NULL` and fills it later. Both ship. CAP-13's consent record is now optional in practice, and CAP-24's erasure audit has rows for customers who never consented. Worse, the two paths race on AD-18's partial unique index `UNIQUE (whatsapp_number) WHERE whatsapp_number IS NOT NULL AND deleted_at IS NULL`: two counters capturing the same returning customer at the same second produce a `23505`, which AD-11 dutifully translates to a 409 — and because AD-10 puts the INSERT inside the checkout transaction with no retry loop (AD-10: "no retry loop exists, because every race in this system is closed by AD-7, AD-8, or AD-9" — this one is closed by none of them), the **entire cart is rolled back** over a duplicate phone number. The customers developer, building a standalone create form, sees the 409 as correct behaviour.
- **The tightening:** name `customers.service.js` as the sole writer of `customers`, exporting `findOrCreateByWhatsapp({...}, { transaction })` which every other service calls; make consent required there and only there. Add the missing race rule to AD-10: the customer lookup-or-create is the one place a `23505` is expected rather than exceptional, and it is resolved by `ON CONFLICT (whatsapp_number) WHERE ... DO NOTHING` followed by a re-select inside the same transaction — not by rolling back the gesture. AD-10's "every race is closed by AD-7/8/9" is currently false, and this is the counter-example.

### H-4 — `expenses` has two writers at settlement, and no guard against writing both

- **Two units:** *Epic Rentals / Settlement (CAP-19)* and *Epic Expenses (CAP-21)*.
- **The AD they both obey:** AD-5 (`expenses` is append-only — INSERT only, corrections are reversing rows), AD-9 (the `expenses_one_reversal` index guards double-*reversal*, not double-*insert*), the domain model's "A damage charge collected at settlement is income against the unit; the repair it funds is a `RENTAL_UPKEEP` expense against the same unit. Both sides show on the unit's ledger."
- **The concrete divergent outcome:** the settlement developer reads that sentence as a system behaviour and auto-INSERTs a `RENTAL_UPKEEP` expense for `damage_charged_paise` against the unit inside the settlement transaction (legal: service-to-service call, one transaction, append-only INSERT). The expenses developer builds the manual entry screen CAP-21 asks for, and the shop's staff — who were charged for a repair by the tailor — enter it. The unit now carries the upkeep twice. `expenses` is append-only, so neither row can be deleted; the correction is a reversing row, which someone must notice is needed. Q13 (per-unit lifetime earnings), Q3 (expenses) and Q23 (ROI) all under-report profit for every damaged rental, and nothing in the schema flags it because no unique constraint exists on `(unit_id, category, incurred_on)` or on a link back to the agreement.
- **The tightening:** decide and state it — the honest answer is that the damage *charge* is income (already in `v_rental_income`) and the repair *cost* is a real, separately-incurred expense that only a human knows the amount of, so settlement must **not** auto-create it. Say so in AD-5 or the Capability Map row for CAP-19/CAP-21: "`expenses.service.js` is the sole writer of `expenses`; no other service INSERTs an expense; a damage charge does not imply an expense row." If auto-creation is wanted instead, add `rental_agreement_id` to `expenses` with a partial unique index `expenses_one_per_agreement`.

### H-5 — "The service layer validates" versus "Zod in the controller": three error shapes for one bad enum

- **Two units:** *Epic Picklists / Units (CAP-3, CAP-10)* and *Epic Sales / Expenses (CAP-12, CAP-21)* — any two developers implementing any two of AD-3's six constrained columns.
- **The AD they both obey:** AD-3 — "the same allowed set is mirrored as a frozen object in `backend/src/constants/`, one file per set, and **the service layer validates** against the constant. The CHECK is the backstop" — and the Conventions row — "Validation: Zod schema in `<name>.validation.js`, **parsed in the controller**, then `next(error)`. Never validate in a route or a model hook."
- **The concrete divergent outcome:** AD-3 names no service. For `unit.status` and `unit.channel` AD-8 assigns `units.service`; for `damage_grade.outcome` the value is *written* by `picklists.service` and *acted on* by `rentals.service`, and both can legitimately claim the validation. More damagingly, the two mandates produce three different responses to the same bad input. Developer A puts the enum in the Zod schema only: `POST /api/sales` with `paymentMethod: "CARD"` → 400, envelope `{ success: false, message, errors: [...] }` with a field path. Developer B puts it in the service only, per AD-3's literal words: `POST /api/expenses` with `category: "FUEL"` → whatever `statusCode` that service picked, envelope `{ success, message }`, no `errors[]`. Developer C does neither and lets the CHECK fire: `23514` → AD-11 translates it by **constraint name**, so the client gets a message keyed on `expenses_category_check`. Three clients, three parsers. AD-11's whole premise — that constraint-name translation is the single funnel — is undermined by the fact that a correctly-built module never reaches it.
- **The tightening:** state the layering once, in AD-3: "the Zod schema in `<name>.validation.js` is the *only* place a constrained string is checked for membership, and it imports the frozen constant — the constant is not re-checked in the service; the service validates *transitions and cross-row rules* (AD-8's `(channel, from, to)` set), not membership; the CHECK is the backstop that no correct request reaches." Then add the constraint-name → message table for all six CHECKs to AD-11 so the backstop path is at least deterministic.

### H-6 — `customer_erasure_audit` is in no AD-5 tier, and AD-4 makes it soft-deletable

- **Two units:** *Epic Customers / Erasure (CAP-24)* — building migration 19. *Epic Reports or any admin screen* — anyone who calls `.destroy()` on a model that AD-4 configured `paranoid: true`.
- **The AD they both obey:** AD-4 — "**Every** new table carries `deleted_at TIMESTAMPTZ NULL`; models set `paranoid: true`" — and AD-5, whose tier table lists twelve tables and does **not** list `customer_erasure_audit` (migration 19) in any of the three tiers.
- **The concrete divergent outcome:** developer A reasons it is obviously an audit trail and treats it as append-only; developer B reads AD-5's tier table as exhaustive, finds the table absent, and falls back to AD-4's universal `paranoid: true`, which makes the row soft-deletable through the ordinary Sequelize path. The proof that a CAP-24 erasure was performed — the one artefact a data-protection question would ever ask for — can be removed by the same administrator who performed the erasure, and AD-18's "an audit row records `customer_id`, actor, and timestamp" becomes unverifiable. `app_settings` has the same problem from the other side: AD-5 puts it in mutable master data, which explicitly permits soft delete, so the CAP-23 exchange window row can be deleted and the window becomes undefined mid-trading.
- **The tightening:** add `customer_erasure_audit` to AD-5's append-only tier explicitly (the tier table must be exhaustive over the migration sequence — audit it against migrations 03–19 and fix every omission). Add a rule for `app_settings`: it is mutable but not deletable — no soft delete, and a `NOT NULL` default for every setting the code reads, so a missing row is impossible rather than merely unlikely.

### H-7 — A soft-deleted `units` row: the views do not agree on whether its history exists

- **Two units:** *Epic Reports / `v_net_sale_lines` + `v_net_expenses` (migration 20)* and *Epic Reports / Q13 (per-unit ledger), Q7, Q10*.
- **The AD they both obey:** AD-4 (`deleted_at` on every table; every partial index predicate excludes it), AD-5 (`units` is **mutable master data** — "Ordinary UPDATE and soft delete"), AD-13 (the three view contracts, none of which mentions `deleted_at`), AD-15 (`units(status) WHERE deleted_at IS NULL`).
- **The concrete divergent outcome:** AD-5 permits soft-deleting a unit, and nothing forbids soft-deleting one that has sale lines, an open rental agreement, or a live booking — AD-8's CAS carries `AND deleted_at IS NULL`, so a soft-deleted rented unit can never be transitioned back, and AD-9's `agreements_one_open_unit` keeps holding its slot forever. On the read side, the view developer building `v_net_sale_lines` does not join `units` at all (the line carries its own price snapshots), so a soft-deleted unit's revenue stays in Q1. The Q13 developer joins `units` for the barcode and, following AD-4's habit, filters `u.deleted_at IS NULL`, so the same unit's ledger vanishes. Q1 and Σ(Q13) no longer reconcile, and the difference is invisible because it is one row.
- **The tightening:** state in AD-5 that a `units` row may be soft-deleted **only** when it has no `sale_lines`, no `rental_agreements`, and no `rental_bookings` in a non-terminal state — enforced in `units.service` and stated as a rule, since no FK can express it (a retired unit uses `status = 'retired'`, not deletion). Then state in AD-13 that **the views never filter on `units.deleted_at`** — history is history — and that any question joining `units` for display joins without the predicate. One sentence in each place removes the whole class.

### H-8 — Per-cashier takings cannot sum to shop takings, because `v_rental_income` has no actor

- **Two units:** *Epic Reports / Q19–Q20 (per-cashier performance)* and *Epic Reports / Q1 (shop takings)*.
- **The AD they both obey:** AD-13 (the three views are the only money surface; the `v_net_sale_lines` contract explicitly "carries the shop-day column and `sold_by_user_id`", the `v_rental_income` contract names no actor column), AD-15 (the index set contains `sales(sold_by_user_id)` and nothing equivalent on `rental_bookings`).
- **The concrete divergent outcome:** Q19 is built on `v_net_sale_lines` grouped by `sold_by_user_id` — retail only, because rental income has no actor to group by. Q1 is built on both views. The owner opens the dashboard, sums the per-cashier column, and it falls short of shop takings by every rupee of rent, damage and forfeiture in the period. There is no reconciliation path and no error: both questions obeyed AD-13 exactly. The domain model does record the actor (`RentalBooking` has `customerId + snapshots` and the migration 15 note says "FK units, customers, **users**"), so the data exists — the view contract simply drops it.
- **The tightening:** add `booked_by_user_id` (rent rows) / `settled_by_user_id` (damage, overdue, forfeiture rows) to the `v_rental_income` contract as a single `actor_user_id` column, and add `rental_bookings(created_by_user_id)` to the AD-15 index set. State the reconciliation identity in AD-14 as a testable property: `Σ over actors of Q19 == Q1` for any range.

### H-9 — The CAP-23 exchange window is mutable master data with no history

- **Two units:** *Epic Sales / Checkout (CAP-14)* and *Epic Sales / Exchange (CAP-23)* — plausibly two developers, certainly two stories.
- **The AD they both obey:** AD-5 (`app_settings` is **mutable master data** — ordinary UPDATE, no history), the Capability Map (`CAP-23 | modules/sales/ | ... app_settings window`), migration 03 ("exchange window (default 7), admin-changeable").
- **The concrete divergent outcome:** a sale is made on 1 September when the window is 7 days. On 5 September the owner shortens the window to 3. On 6 September the customer arrives to exchange. Developer A snapshotted `exchange_window_days` onto the `sales` row at checkout (the ledger-tier instinct — everything else on a sale is a snapshot: price, buying price, customer name, WhatsApp) and accepts the exchange. Developer B reads `app_settings` at exchange time (the literal reading of "admin-changeable") and refuses it. The same sale, the same day, two answers — and the refusal is *retroactive*, changing the terms of a completed transaction, which is precisely the property AD-5's ledger tiers exist to prevent. The `sales` table has no column for the snapshot, so Developer A must add one, and Developer B's story will not know it exists.
- **The tightening:** add `exchange_window_days SMALLINT NOT NULL` to `sales` (migration 13) as a snapshot taken at checkout, and state in AD-5 that **any `app_settings` value that constrains a future decision about a completed transaction is snapshotted onto that transaction row at write time; `app_settings` is read only for new transactions.** That is a general rule and it will cover the next setting too.

### H-10 — Three copies of `deposit_paise` / `overdue_per_day_paise`, and no named authority

- **Two units:** *Epic Rentals / Booking (period cap validation)* and *Epic Rentals / Settlement + Epic Reports / Q11–Q12 (overdue accrual)*.
- **The AD they both obey:** AD-16 ("maximum rental period is `floor(deposit_paise / overdue_per_day_paise)` ... evaluated in the SELECT that renders the page") and the domain model, which puts `rentPerDayPaise`, `depositPaise`, `overduePerDayPaise` as snapshots on **`Unit`** (from the lot), `depositPaise` on **`RentalBooking`**, and `rentPerDayPaise`, `depositPaise`, `overduePerDayPaise` on **`RentalAgreement`** ("snapshots taken from the unit at booking").
- **The concrete divergent outcome:** three columns hold the same concept in three tables and staff may override the deposit at booking. The booking developer validates the period cap against `units.deposit_paise` (the lot default). The settlement developer accrues overdue against `rental_agreements.overdue_per_day_paise`. The Q12 developer renders the maximum period against whichever table their JOIN already had. A booking where staff waived half the deposit passes the cap check on the unit's full deposit and is then out for twice as long as the deposit covers — the exact exposure AD-16's formula exists to bound. For a walk-in, where booking and hand-over are one transaction, `rental_agreements.deposit_paise` and `rental_bookings.deposit_paise` are guaranteed equal; for a booked path with any override between the two, nothing guarantees it.
- **The tightening:** state the authority chain once, in AD-7 or AD-16: "`units.*` are lot defaults and are read only to pre-fill the booking form. `rental_bookings.deposit_paise` / `rent_charged_paise` / `overdue_per_day_paise` are the transaction's terms and are the sole authority for the period cap. `rental_agreements.*` are copied from the **booking**, never from the unit, and are the sole authority for settlement and every read-side computation." Add `overdue_per_day_paise` to `rental_bookings` (migration 15), which currently lacks it while AD-16's formula needs it at booking time.

### H-11 — A forfeited deposit is counted twice, or not at all

- **Two units:** *Epic Reports / `v_rental_income`* and *Epic Rentals / Settlement*.
- **The AD they both obey:** AD-13's `v_rental_income` contract — "Rent ..., damage charges (anchored to `returned_at`), and **forfeited deposits (anchored to the `lost` transition)**" — and AD-14's anchor table, "`unit_status_events` → `occurred_at` → Shrinkage and forfeiture are events", together with the domain model's `depositReturnedPaise` written once at settlement.
- **The concrete divergent outcome:** two forfeiture mechanics are described and the spine sanctions both. Mechanic A: the unit is never returned, staff mark it `lost`, a `unit_status_events` row fires, and the forfeited income is the agreement's full `deposit_paise` anchored to `occurred_at`. Mechanic B: the customer returns the unit ruined, settlement writes `damage_charged_paise` and `deposit_returned_paise = 0`, and the forfeited amount is `deposit_paise - deposit_returned_paise` anchored to `returned_at`. If the view developer implements both branches without an exclusivity predicate, a beyond-repair return that is *also* marked `lost` (damage-grade outcome `RETIRE` plausibly drives exactly that transition) is counted **twice** — once as damage, once as forfeiture. If they implement only the `lost` branch, a partial forfeiture through `deposit_returned_paise < deposit_paise` is income that appears nowhere.
- **The tightening:** define forfeiture arithmetically, once: `forfeited = deposit_paise - COALESCE(deposit_returned_paise, 0) - damage_charged_paise - overdue_charged_paise`, anchored to `returned_at` when the agreement is settled and to the `lost` event's `occurred_at` when it is not, with the two branches mutually exclusive on `returned_at IS NULL`. Add the `CHECK (deposit_returned_paise + damage_charged_paise + overdue_charged_paise <= deposit_paise)` that makes the identity a database fact, named `rental_agreements_deposit_split_check`.

### H-12 — `rental_agreements.reverses_agreement_id` is a reversal pointer AD-9 forgot

- **Two units:** *Epic Rentals / Settlement corrections* and whoever owns AD-9's migration.
- **The AD they both obey:** AD-9 — "**Every** reversal pointer carries a partial unique index" — which then lists exactly three, none of them `rental_agreements`. The domain model's RentalAgreement carries `reversesAgreementId` ("For corrections"), and migration 16's description does not mention the column at all.
- **The concrete divergent outcome:** a mis-settled agreement is corrected by a reversing agreement row. Nothing stops a second one. Damage and forfeiture income double-subtract in `v_rental_income` — the exact failure AD-9's preamble names ("producing a takings figure that silently double-subtracts"). Meanwhile a reversing agreement row has `returned_at` set (or not), which interacts unpredictably with `agreements_one_open_unit`. The column also does not appear in migration 16's column list, so one developer may not build it at all while another builds the correction flow against it.
- **The tightening:** add `agreements_one_reversal` — `CREATE UNIQUE INDEX ON rental_agreements(reverses_agreement_id) WHERE reverses_agreement_id IS NOT NULL AND deleted_at IS NULL` — to AD-9's list and `reverses_agreement_id` to migration 16's description. Also state whether a reversing agreement participates in `v_rental_income` (it must, negatively) and whether it is exempt from `agreements_one_open_unit` (it must be — set `returned_at` on it at insert).

## MEDIUM

### M-1 — The walk-in booking never passes through `open`, and two developers model that differently

- **Two units:** *Epic Rentals / Walk-in hand-over* and *Epic Rentals / Booked hand-over + Epic Reports / Q22 ("booked not collected")*.
- **The AD they both obey:** AD-10 (one transaction per gesture — a walk-in is one gesture), AD-7 (the EXCLUDE predicate covers `open` and `handed_over` identically, so inserting straight at `handed_over` is guarded the same), AD-5 tier 2 (`open → handed_over → settled|cancelled`), and the domain model's "Created at booking, **or in the same transaction as hand-over for a walk-in**".
- **The concrete divergent outcome:** developer A inserts the walk-in booking directly with `state = 'handed_over'` — one INSERT, one gesture, EXCLUDE satisfied. Developer B, reading AD-5's tier-2 lifecycle as beginning at `open`, inserts `state = 'open'` and then runs the state CAS to `handed_over` in the same transaction, so the row passes through both states. The rows differ: A's booking has no moment at which the booked path's validation (availability check, period cap, deposit collection) ran as a distinct step, and A's `rental_bookings` row can never be reached by any code that assumes `state = 'open'` precedes hand-over — including any future "modify booking before collection" flow. Q22 ("booked not collected") is `state = 'open'` under both, so it is accidentally correct; but a hand-over CAS written as `UPDATE rental_bookings SET state='handed_over' WHERE state='open'` — the natural AD-8-shaped guard — silently never runs for walk-ins, so whatever guard it carried is skipped on the busiest path.
- **The tightening:** state in AD-7 or the CAP-17/CAP-18 map row that a walk-in inserts at `state = 'open'` and advances by the same CAS as the booked path, in the same transaction — so there is exactly one hand-over code path and one set of rows. Say explicitly that the booking-state transition is an AD-8-shaped compare-and-swap (`WHERE state = :expectedFrom`), which the spine currently only specifies for `units.status` and `rental_agreements.returned_at`.

### M-2 — `units.channel` is written by two modules

- **Two units:** *Epic Intake (CAP-7/8/9)* — "channel: Copied from the lot at intake" — and *Epic Units (CAP-11)* — the retail↔rental conversion, mapped to `modules/units/`.
- **The AD they both obey:** AD-8 (which reserves only `units.status` — "no other module may write `units.status` directly" — and says nothing about `channel`), AD-3 (`unit.channel` is a constrained string), AD-5 (`units` is mutable master data).
- **The concrete divergent outcome:** intake writes `channel` at creation with no validation beyond the CHECK; units.service writes it on conversion with a legality guard (a rented unit cannot flip to retail; a rental→retail flip must null the rental snapshots or they lie). Since AD-8's `(channel, from, to)` guard keys **on** channel, a channel written by intake without going through that guard can put a unit into a state the guard considers illegal — e.g. a rental-channel unit created directly at `status = 'rented'`. Also unsaid: does conversion carry the `rent_per_day_paise` / `deposit_paise` / `overdue_per_day_paise` snapshots with it? Intake copies them from the lot; conversion has no lot to copy from.
- **The tightening:** extend AD-8's sole-writer clause to `units.channel` and the three rental snapshot columns, and state that a retail→rental conversion requires the three rental price snapshots as explicit inputs (there is no lot to inherit from), while a rental→retail conversion nulls them and is refused unless `status = 'in_stock'` with no open booking.

### M-3 — `group_id` has no defined generator, no table, and no defined cancellation granularity

- **Two units:** *Epic Rentals / Booking (the group receipt)* and *Epic Rentals / Settlement + Cancellation*.
- **The AD they both obey:** AD-1 (the API speaks `uuid`; FKs reference `id` — `group_id` is a UUID that is an FK to nothing, since no groups table exists in the migration sequence), AD-10 ("a **settlement** is one transaction scoped to one unit's agreement, leaving its group siblings untouched"), the domain model (`groupId` "shared by every booking made in one counter interaction. Drives the single receipt", and also present on `RentalAgreement`).
- **The concrete divergent outcome:** developer A generates `group_id` in the service with `crypto.randomUUID()`; developer B uses a column `DEFAULT gen_random_uuid()` and then has to overwrite it for siblings 2..n. On the agreement side, A copies the booking's `group_id`; B generates a fresh one per hand-over gesture — which is arguably right, since a 3-unit booking group may be collected on two different days. Whichever, the group receipt (CAP-18) joins on `group_id` and returns a different set under each. Cancellation granularity is equally open: AD-10's "one transaction per gesture" makes cancelling a 3-unit group either one gesture (three rows advance together, one refund) or three gestures (three refunds, partial cancellation legal). The refund figure and the receipt differ.
- **The tightening:** state that `group_id` is generated by the service once per gesture and is `NOT NULL` on both tables; that the **agreement's** `group_id` is generated at hand-over and is not the booking's, because collection may split a booking group; that a group receipt is addressed by booking `group_id` at booking and agreement `group_id` at hand-over; and that cancellation is per-booking-row, with a group cancellation being N such gestures — or one, but pick one and say it.

### M-4 — Non-money questions have no mandated shop-day conversion

- **Two units:** *Epic Reports / any question anchored on `unit_status_events.occurred_at`* (shrinkage, forfeiture) and *Epic Reports / any question anchored on `rental_agreements.returned_at`*.
- **The AD they both obey:** AD-6 ("Wherever a timestamp must be reduced to a shop day, it is done in SQL as `(<col> AT TIME ZONE 'Asia/Kolkata')::date`"), AD-13 (which mandates the shop-day column on `v_net_sale_lines` and `v_net_expenses` — and **not** on `v_rental_income`, whose contract mentions anchoring but not a shop-day column), AD-14 (half-open ranges on the shop day).
- **The concrete divergent outcome:** money questions inherit the conversion from the views. Non-money range questions — and `v_rental_income` itself, whose contract omits the column — must each do it themselves. Developer A writes `WHERE occurred_at >= :from AND occurred_at < :to + 1`, comparing a `TIMESTAMPTZ` to a `DATE` and getting UTC midnight boundaries; developer B writes AD-6's expression. Every event between 00:00 and 05:30 IST lands on the previous shop day under A. On a shop that closes at 21:00 IST this is rare enough to survive testing and appear once a quarter, on exactly the days the owner is reconciling.
- **The tightening:** state in AD-13 that **all three** views carry a `shop_day DATE` column computed by AD-6's expression, and in AD-14 that a question may filter only on a `shop_day` column, never on a raw `TIMESTAMPTZ` — making the raw comparison a reviewable, greppable violation. For `unit_status_events`, add a `shop_day` to whatever view or CTE serves it and index it (AD-15 currently indexes "each anchor column", i.e. the raw timestamp, which the correct expression will not use — see L-3).

### M-5 — Changing a booking's dates: legal only as cancel-and-rebook, which double-charges rent

- **Two units:** *Epic Rentals / Booking amendments* and *Epic Rentals / Cancellation*.
- **The AD they both obey:** AD-5 tier 2 — "UPDATE permitted **only** to advance the row toward its terminal state" — which forbids editing `start_date` / `end_date`; and the domain model's "**Never recomputed:** rent. It was charged in full at booking and is not pro-rated for an early return, a late collection, a cancellation, or a no-show."
- **The concrete divergent outcome:** the customer moves their wedding by a week. The only AD-compliant path is cancel + rebook. Under C-4's unresolved policy, the cancellation forfeits the rent, so the customer pays rent twice for one rental. Developer A implements the amendment as an UPDATE anyway (it is the obviously right behaviour, and AD-5's rule reads as being about *settled* rows); developer B implements cancel + rebook and hands the customer a second bill. Note also that AD-7's EXCLUDE makes the compliant path fail for an *extension*: the new booking's range overlaps the old one until the old one is cancelled, so the order of operations inside the transaction is load-bearing and unspecified.
- **The tightening:** state the amendment policy explicitly in AD-5's tier-2 row: either name `start_date`/`end_date` as amendable-while-`open` (with the EXCLUDE constraint still doing its job, since the generated `period` recomputes on UPDATE — worth stating, because that is a non-obvious property builders will not assume), or state that amendment is cancel-and-rebook with rent carried across, and give it a column (`rent_credited_from_booking_id`). The first is simpler and does not breach the ledger paradigm, because an `open` booking is not yet a completed transaction.

### M-6 — Editing a unit's price snapshots after it has sold

- **Two units:** *Epic Intake / unit edit (CAP-8)* and *Epic Reports / Q13 (per-unit ledger), Q16 (sell-through), Q23 (ROI)*.
- **The AD they both obey:** AD-5 (`units` is mutable master data — "Ordinary UPDATE"), AD-13 (whose `v_net_sale_lines` carries `net_buying_paise` from the **sale line's** snapshot).
- **The concrete divergent outcome:** a staff member corrects a typo in `units.buying_price_paise` a month after the unit sold. `sale_lines.buying_price_paise` was snapshotted at checkout and does not move, so Q1 margin is unchanged. Any question reading `units.buying_price_paise` — the natural source for aging, sell-through and unsold-stock valuation — now uses the new figure. Q13's per-unit ledger and Q1's margin disagree for that unit, permanently, with both obeying every AD.
- **The tightening:** state in AD-5's mutable row that `units.buying_price_paise`, `selling_price_paise`, `floor_price_paise` and the three rental snapshots are **frozen once the unit leaves `in_stock` for the first time** — enforced in `units.service` — and state in AD-13 that unsold-stock valuation reads `units.*`, realised figures read `sale_lines.*`, and no question mixes the two.

### M-7 — AD-10's exchange paragraph omits the status event its own diagram mandates

- **Two units:** *Epic Sales / Checkout* and *Epic Sales / Exchange (CAP-23)* — the same module, two stories, plausibly two people.
- **The AD they both obey:** AD-10, whose sequence diagram for checkout includes `INSERT unit_status_event` inside the loop, and whose exchange paragraph enumerates the exchange's contents — "reverse the incoming line ..., CAS the incoming unit `sold → in_stock`, then run the outgoing unit through the checkout path above, and record the signed `exchange_difference_paise`" — with no event insert for the incoming unit's `sold → in_stock`.
- **The concrete divergent outcome:** the outgoing unit gets an event (it goes through the checkout path); the incoming unit does not. `unit_status_events` is no longer the complete history the domain model claims ("the unit's `status` column is a cached projection of the latest event" — the projection now disagrees with the latest event). Q13's per-unit ledger shows a unit that sold and never came back, then sold again with no event between. Combined with C-2, the same transition may be written zero times here and twice on the checkout path.
- **The tightening:** once C-2 makes `units.service.transitionUnit()` the sole path, this closes automatically — every CAS carries its event. Until then, amend AD-10's exchange paragraph to name the event insert. Add the test AD's Conventions already imply: an invariant test asserting `units.status` equals the `to_status` of the latest `unit_status_events` row for every unit.

### M-8 — `rent_charged_paise` (booking total) versus `rent_per_day_paise` (agreement) with no stated authority

- **Two units:** *Epic Rentals / Booking* and *Epic Reports / Q13, Q24 (unit lifetime earnings, utilisation)*.
- **The AD they both obey:** AD-13's `v_rental_income` ("Rent, anchored to the booking's creation shop-day") and the domain model, which stores a *total* `rentChargedPaise` on the booking and a *per-day* `rentPerDayPaise` on the agreement.
- **The concrete divergent outcome:** staff discount a booking — three days at ₹500 charged as ₹1,200. `rental_bookings.rent_charged_paise = 120000`; `rental_agreements.rent_per_day_paise = 50000`. The view developer takes the booking total (correct, and what AD-13 implies). Any question computing "average rent per day" or "utilisation-weighted earnings" that reaches for the agreement's per-day snapshot gets ₹1,500. Because both are snapshots and neither is derived, no constraint notices. The discount is also invisible: nothing records that it happened or who authorised it.
- **The tightening:** state that `rental_bookings.rent_charged_paise` is the only rent figure that is ever summed, that `rental_agreements.rent_per_day_paise` exists solely as the reference for computing what *would* have been charged, and add `rent_list_paise` (rent_per_day × days) to `rental_bookings` so the discount is a visible, reportable difference rather than an absence.

### M-9 — A handed-over booking whose unit is lost never reaches a terminal state

- **Two units:** *Epic Rentals / Settlement (the `lost` outcome)* and *Epic Rentals / Availability (CAP-17)*.
- **The AD they both obey:** AD-5 tier 2 (`open → handed_over → settled|cancelled` — with no arc for "never came back"), AD-7 (the EXCLUDE predicate covers `handed_over`), AD-9 (`agreements_one_open_unit ... WHERE returned_at IS NULL`).
- **The concrete divergent outcome:** the customer vanishes with the piece. Developer A settles the agreement (`returned_at` set, `deposit_returned_paise = 0`, damage grade "Beyond repair") and advances the booking to `settled`, then fires the `lost` unit transition — the booking terminates, the EXCLUDE releases, the forfeiture is anchored to `returned_at`. Developer B refuses to write `returned_at` on a unit that never returned (it would be a lie in an audit trail), leaves the booking at `handed_over` forever, and fires only the `lost` event — so the EXCLUDE constraint holds a dead unit's dates in perpetuity, `agreements_one_open_unit` holds its slot, the tier-2 freeze never applies so the row stays editable forever, and C-4/H-11's forfeiture anchoring picks the other branch. Both readings are defensible; the rows are irreconcilable.
- **The tightening:** add a `written_off` terminal state to `rental_bookings.state` (AD-3's constrained set) and a `written_off_at` to `rental_agreements` that satisfies both the EXCLUDE predicate's exclusion and AD-9's index predicate — i.e. make the two partial predicates `WHERE state IN ('open','handed_over')` and `WHERE returned_at IS NULL AND written_off_at IS NULL`. Then state that forfeiture on a write-off is anchored to `written_off_at`, closing H-11's second branch.

## LOW

### L-1 — `damage_grades` reaches AD-5's mutable tier only by inference
AD-5's tier table says "all picklists"; whether `damage_grades` is a picklist is established only by the Source-tree comment (`picklists/ # product types, colours, sizes, damage grades`). It matters because `default_charge_paise` is a money column on a soft-deletable row that settled agreements snapshot from. Name it in the tier table, and state that `damage_grade_id` on a settled agreement is never resolved for its current `default_charge_paise` — `damage_charged_paise` is the snapshot.

### L-2 — AD-17's startup `setval` has no owner, and AD-16 forbids the obvious home
AD-17 says "**Startup** runs `setval('barcode_seq', GREATEST(...))`". AD-16 forbids "no second entry point beyond `server.js`". So it must live in `server.js` boot — but AD-19.3 says the app connects through a transaction-mode pooler where "nothing in the code may depend on session state surviving between statements", and a container host that spins down and back up runs it on every cold start, i.e. many times a day. Say where it lives (`server.js`, before `app.listen`, one statement, idempotent) and note that repeated execution is harmless — otherwise a developer will put it in a migration, where it runs once and misses every restore.

### L-3 — The AD-15 index set does not match the queries AD-6 and AD-14 mandate
"b-tree on each anchor column in AD-14" indexes raw `sold_at`, `returned_at`, `occurred_at`, but AD-6 requires every day-boundary filter to be `(<col> AT TIME ZONE 'Asia/Kolkata')::date`, which a plain b-tree on the raw column cannot serve. Either the indexes must be expression indexes on `((col AT TIME ZONE 'Asia/Kolkata')::date)`, or the questions must filter on a half-open `TIMESTAMPTZ` range derived from the shop-day bounds (which is sargable and preferable). Say which. Also missing from the set: `sales(customer_id)` — required by AD-18's own correction to Q21 ("Q21 must match on `sales.customer_id`") — and `unit_status_events(unit_id)`, needed by Q13's per-unit ledger, which the set covers for `sale_lines`, `rental_agreements` and `expenses` but not for events.

### L-4 — AD-9 does not guard `sales.reverses_sale_id`
Migration 13 creates the self-FK. AD-9's index list covers `sale_lines.reverses_sale_line_id` and, by the line-level index, effectively blocks a double reversal of any line — but a header-level double reversal with zero or disjoint lines is unguarded, and the exchange path writes both a header and lines. Add `sales_one_reversal ON sales(reverses_sale_id) WHERE reverses_sale_id IS NOT NULL AND deleted_at IS NULL` for symmetry and for AD-11's constraint-name table.

### L-5 — `rental_bookings` has no `deleted_at`-driven cancellation path, which is correct but unstated
AD-4's motivating example is "a cancelled-and-deleted booking permanently blocking its dates", and the EXCLUDE predicate carries `deleted_at IS NULL` accordingly. But AD-5 tier 2 forbids soft-deleting a booking at all (only advancing UPDATEs), so `deleted_at` on `rental_bookings` is dead by policy and live by predicate. Harmless, but the predicate implies a path that the tier forbids, and a builder will eventually take it. One sentence: "on tier-2 tables `deleted_at` exists for uniformity and predicate symmetry only, and is never written" — the same sentence AD-4 already gives for tier-1 tables.
