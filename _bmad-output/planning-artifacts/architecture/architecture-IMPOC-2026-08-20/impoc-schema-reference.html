03 Race guards

Every race in this system is closed by the database, not by application locking. That is why isolation stays READ COMMITTED and no retry loop exists.

Rental overlap — the exclusion constraint

-- migration 01, alone and first: fails loudly if the host forbids it
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- generated, never declared on the Sequelize model
period daterange GENERATED ALWAYS AS (daterange(start_date, end_date, '[]')) STORED

ALTER TABLE rental_bookings
  ADD CONSTRAINT rental_bookings_no_overlap
  EXCLUDE USING gist (unit_id WITH =, period WITH &&)
  WHERE (state IN ('OPEN', 'HANDED_OVER') AND deleted_at IS NULL);
Bounds are '[]' — inclusive both ends, because a piece due back on the 17th is out on the 17th. That is also why rentalDays = (end_date − start_date) + 1 (AD-23). Sequelize 6 addConstraint has no exclusion type, so this is raw queryInterface.sequelize.query() DDL with a matching raw DROP in down().
The generated column recomputes on UPDATE. That is what makes AD-31's amend-while-OPEN safe: changing the dates re-checks the exclusion constraint automatically, and an extension needs no cancel-then-rebook ordering dance.

Unit movement — compare-and-swap

-- units.service.js only. Sole writer of status, channel,
-- the three rental snapshots, AND unit_status_events.
UPDATE units SET status = :to
 WHERE id = :id AND status = :expectedFrom AND deleted_at IS NULL
RETURNING id;
A booked unit cannot leave the floor. Any transition out of IN_STOCK other than hand-over is refused with a 409 whenever an open booking covers today or later, and the error names the booking, its window and the customer. Staff cancel the booking first — which refunds the deposit through AD-27. The damage transition deliberately does not auto-cancel: one gesture must never silently move a third party's money.

Booking state — the same shape

UPDATE rental_bookings SET state = :to
 WHERE id = :id AND state = :expectedFrom AND deleted_at IS NULL
RETURNING id;

A walk-in INSERTs at OPEN and advances through this same statement, so there is exactly one hand-over path. Inserting straight at HANDED_OVER would give the busiest path a row shape no WHERE state = 'OPEN' guard can reach.

One reversal per row, one open agreement per unit

CREATE UNIQUE INDEX sales_one_reversal       ON sales(reverses_sale_id)
  WHERE reverses_sale_id IS NOT NULL AND deleted_at IS NULL;
CREATE UNIQUE INDEX sale_lines_one_reversal  ON sale_lines(reverses_sale_line_id)
  WHERE reverses_sale_line_id IS NOT NULL AND deleted_at IS NULL;
CREATE UNIQUE INDEX expenses_one_reversal    ON expenses(reverses_expense_id)
  WHERE reverses_expense_id IS NOT NULL AND deleted_at IS NULL;
CREATE UNIQUE INDEX agreements_one_open_unit ON rental_agreements(unit_id)
  WHERE returned_at IS NULL AND written_off_at IS NULL AND deleted_at IS NULL;

The header-level index matters because the exchange path writes both a header and lines: without it a double reversal with zero or disjoint lines slips past the line-level guard. The last carries written_off_at IS NULL so AD-32's write-off releases the unit's slot.

Transaction boundaries

Checkout

One transaction

Re-read units → INSERT sale → per line: transitionUnit to SOLD (status + event together) + sale_line → COMMIT → then render the receipt.

Exchange

One transaction, both halves

Reverse the incoming line, transition SOLD → IN_STOCK, run the outgoing unit through checkout, record the signed difference.

Settlement

Scoped to one unit

CAS on returned_at IS NULL, compute overdue at settlement, transition the unit to its outcome. Group siblings stay open.

Nothing that is not Postgres I/O may happen inside a transaction. No PDF render, no barcode encode, no HTTP call, no file write. Receipts are generated after commit, from committed rows.

04 Barcode format

Redesigned so that uniqueness never depends on durable state a restore can rewind. The old pure-sequence scheme could reissue a number already printed on a label; this one structurally cannot.

MMMMMMMCCCCC   -- 12 digits, zero-padded, digits only
└──────┘└───┘
   │       └─ 5 digits: nextval('barcode_seq') % 100000
   └───────── 7 digits: whole minutes since 2026-01-01 00:00 Asia/Kolkata
Why the minute prefix. A restore takes far longer than a minute, so the minute the system comes back up in has never issued a label. A printed-but-unscanned sheet stays valid after a restore instead of having to be discarded — and CAP-2's “the sequence never rewinds” is met literally rather than approximately. The boot setval and the whole post-restore discard procedure are gone.
FieldCapacityExhausted
7 minute digits10,000,000 min≈ 19 years, so 2045
5 counter digits100,000 / minNever, at one shop
Two collisions remain conceivable, and are named rather than hidden. Issuing 100,000 labels inside one minute wraps the counter — that is the stated ceiling, not a defect. A backwards server clock jump (NTP correction, host migration) could repeat a minute; far rarer than the restore case it replaces, and units.barcode UNIQUE stops being the primary defence and becomes a genuine last resort.
DigitsModules incl. quiet zoneX-dimension at 35 mmVerdict
101100.318 mmAlternate layout (7+3)
121210.289 mmdefault 7+5
141320.265 mmMarginal, not offered

Digits only, so the encoder stays in Code 128 subset C at two digits per symbol; a letter prefix forces subset B and breaks the 35 mm. Width is structural — only 12 (7+5) and 10 (7+3) exist, both even as subset C requires. As CAP-1 insists, the number that settles this is a caliper reading against a physical print.

05 The five views

The only surface any question reads. No takings, margin, expense, deposit or event query may select from the underlying tables directly. This prevents the highest-value divergence in the system: twenty-four questions each independently remembering to exclude reversing rows.

ViewContract
v_net_sale_linesOne row per sale line, net_price_paise and net_buying_paise already signed. Reversing lines carried as negatives, reversed originals still present so they cancel. Carries shop_day, sold_by_user_id, unit_id, customer_id.
v_net_expensesExpenses with reversals netted, one row per live expense, carrying unit_id and shop_day.
v_rental_incomeOne signed stream over four kinds: rent (anchored to booking creation), damage and overdue (anchored to returned_at), forfeited_deposit (anchored to the LOST transition, or to written_off_at on a write-off). A cancelled booking's rent is income.
v_deposits_heldOne row per deposit currently held, from OPEN and HANDED_OVER bookings and open agreements. The single surface for Q6, Q11 and settlement.
v_unit_status_eventsnew One row per status event with from_status, to_status, actor_user_id and shop_day. Exists so non-money event questions never reduce a timestamp themselves.
One rent figure is summable. rental_bookings.rent_charged_paise (a total) is the only rent ever aggregated. rental_agreements.rent_per_day_paise is reference only. rent_list_paise makes a staff discount a visible, reportable difference rather than an invisible absence.
Realised versus unrealised is a hard split. Unsold-stock valuation and aging read units.*; every realised figure reads v_net_sale_lines.*. No single question mixes the two.

06 The 24 dashboard questions

Each ships as reports/questions/q<n>.js exporting summary() and lines() — a total the owner cannot open is not an answer. Range filtering is only ever done on a shop_day DATE column exposed by a view, never on a raw timestamp.

Row sourceAnchorBecause
v_net_sale_linessale.sold_atThe sale happened then.
v_rental_income (rent)booking.created_atRent lands in the range the booking was made; settlement moves no revenue.
v_rental_income (damage)agreement.returned_atThe charge is assessed at settlement.
v_net_expensesexpense.incurred_onAlready a shop-local date.
stock_intakespurchased_onAlready a shop-local date.
v_unit_status_eventsoccurred_atShrinkage and forfeiture are events. Reached through the view, never the table.
A reversal anchors to the reversing row's own shop day, never the original's. A September sale exchanged in October leaves September's takings exactly as they closed and carries the negative in October. Anchoring to the original would retroactively mutate a period the owner has already read and acted on — the reporting equivalent of UPDATEing a completed transaction.

Point-in-time, not range: Q6 (deposits held), Q7 (on the floor), Q11/Q12 (out on rent, overdue), Q15 (in the workshop) and Q22 (booked not collected) answer “right now” and ignore from/to. Each says so in its file header.

09 Role matrix

AD-29. RENTALS.* is five verbs, one per counter gesture, and the granularity is deliberate: SETTLE and CANCEL move deposit money out of the drawer, BOOK and HANDOVER move it in.

RoleHolds
ADMINEverything, including CUSTOMERS.ERASE and SETTINGS.MANAGE, which no other role holds.
MANAGERExisting set, plus all five RENTALS.*, INVENTORY.BARCODE_GENERATE, and the exchange path that refunds a cash difference.
INVENTORY_MANAGERExisting inventory set, plus INVENTORY.BARCODE_GENERATE. No counter gestures.
CASHIERMoney-in only: SALES.CREATE, RENTALS.VIEW/BOOK/HANDOVER, CUSTOMERS.VIEW/CREATE. Not SETTLE, not CANCEL, not a refunding exchange.
ACCOUNTANTRead-only over money: EXPENSES.*, REPORTS.VIEW, SALES.VIEW, RENTALS.VIEW. Never moves a unit or a customer.

Every route carries authorize(PERMISSIONS.X.Y); never a role-name test. Navigation renders only what the user holds, so a withheld gesture is absent, not disabled.

11 Upstream conflicts

Six places where this spine contradicts a document upstream of it. Each is a decision that must be reconciled at the source, not worked around in code.

vs domain-model.md

The checkout guard makes exchange impossible

A unique constraint on unitId across non-reversing sale lines would mean a unit could never be resold after an exchange, since the original line stays non-reversing. Replaced by AD-8's compare-and-swap.

vs dashboard-questions.md

Q21 cannot match on WhatsApp number

The number is released on erasure, so history detaches and a new person reusing it merges with the old one's sales. Q21 must match on sales.customer_id.

vs domain-model.md

Rental days are off by one

endDate − startDate charges two days for a 15th–17th booking the exclusion constraint holds for three. AD-23 supersedes it.

vs EXPERIENCE.md

Cashier does not see all of Counter

The UX doc builds navigation on “CASHIER sees all of Counter”. AD-29 withholds settle, cancel and refunding exchange. Nav is permission-driven so no rework follows — but the stated intent is now stale.

vs SPEC.md

Identity document is answered, not open

No ID is ever captured: rent plus deposit exceeds the unit's buying price, so a piece that never returns has already been paid for. The spec still lists this as an open question.

vs EXPERIENCE.md

“Receipt saved in db” means reproducible

No PDF bytes are persisted. The rows are durable and the document regenerates identically from snapshots, re-openable forever from the sale or the rental group.
