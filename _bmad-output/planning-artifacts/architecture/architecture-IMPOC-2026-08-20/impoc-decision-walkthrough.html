Architecture rationale · SPEC-impoc-core

The calls that shaped IMPOC

The spec fixed the stack, the module layout, and the conventions. It left a handful of things genuinely open. This is what was weighed on each, what was chosen, and the divergence each choice exists to prevent. Revised after a second pass that re-triaged every reviewer finding, and after two calls Raviraj made directly.

Every decision below was made against a constraint the spec states plainly and does not negotiate: a completed transaction is never updated, nothing derivable is stored, and no cron, scheduler, or background worker may exist. Those three rule out most of the obvious answers, which is what makes the remaining choices worth writing down.

Rationale lives here. The enforceable rules live in the spine, and where the two differ, the spine wins.

01

Rental availability, now that reserved is gone

Asked: overlapping-date-range query — and should it use Postgres range types and exclusion constraints?

The tension

A saree booked for the 14th–17th must still be bookable for the 5th–7th, and it sits IN_STOCK the whole time. So availability is a question about ranges, not a flag. But two clerks can ask that question in the same second and both get “yes”.

○

Two date columns and an overlap query

Simplest, and reads naturally. But the check and the insert are separate statements — nothing stops two overlapping bookings committing together. It reintroduces the race the spec spent reserved to avoid.

○

A native daterange column

Correct, and the constraint works. But the domain speaks start and end dates — that is what the receipt prints and what due_date derives from — and Sequelize’s range bound semantics are easy to get subtly wrong on every write.

●

Canonical dates plus a generated range, under a partial EXCLUDE

Keeps start_date/end_date as the domain columns; adds period as a generated column that exists only to be constrained and indexed.

The call

A generated column cannot drift from its source — Postgres guarantees the two views agree, rather than application code remembering to. Sequelize never needs to know period exists. The guard is EXCLUDE USING gist (unit_id WITH =, period WITH &&), scoped by a WHERE predicate to open and handed-over bookings only.

Bounds are inclusive on both ends, because a piece due back on the 17th is out of the shop on the 17th.

This follows the spec’s own stated principle rather than departing from it: the database constraint is the race guard, not application locking. An exclusion constraint is simply what a unique constraint becomes when the thing that must not collide is a range.

AD-7AD-23
Verified, not assumed: Sequelize 6’s addConstraint has no exclusion type, so this is raw DDL in the migration. btree_gist is needed to mix the equality column with the range — and it is a trusted extension, so the free-tier Postgres you plan to host on can install it without superuser.
Conflict found

Inclusive bounds exposed an off-by-one in the spec itself. endDate − startDate charges two days for a 15th–17th booking that holds the piece for three — so rent, the floor(deposit / overduePerDay) cap, and utilisation were all short, in the customer’s favour. One named formula now governs everywhere: rentalDays = (end − start) + 1.

02

Twenty-four derived questions, no cron

Asked: query and index strategy for the derived-on-read dashboard. (The spec says 21; the catalog lists 24.)

The tension

Every figure must be computed at read time, drillable to its rows, and reconcile exactly — takings minus reversals equalling the sum of the underlying lines. Twenty-four questions, each netting reversing rows, is twenty-four chances to get it wrong once and show a reversed sale as revenue.

○

ORM aggregation with eager loading

Unwritable at this shape, and the query plans are catastrophic. Worse, it invites half the dashboard being built one way and half another.

○

Materialized views

Fast and tidy — and immediately illegal. A matview needs refreshing, and the refresh is the cron the spec bans.

●

Plain views that own netting, read by hand-written SQL

Four plain views compute netting and the shop-day once. A reports module of parameterised SQL reads only those.

The call

Netting moves out of the questions and into four views — sale lines, expenses, rental income, and deposits held. No takings, margin, expense, or deposit query may touch a base table. That single rule is the highest-value invariant in the spine, because it converts twenty-four independent chances to forget into one place to get right.

Each question is one file exporting both a summary and a drill-down — a total the owner cannot open is not an answer — and declares exactly one range anchor, so “which timestamp puts this row in the range” is never decided twice.

On indexes: at one shop’s volume, order 10⁴ units over five years, every one of these runs in milliseconds. The index set exists for plan-shape consistency, not speed. There is deliberately no cache, no read replica, and no summary table.

AD-12AD-13AD-14AD-15AD-16
Prevents: the moment someone looks at an awkward overdue query and reaches for a nightly job. Overdue is a WHERE clause evaluated in the SELECT that renders the page — if a query tempts a scheduler, the query is wrong.
03

Transaction boundaries and the race guards

Asked: boundaries and unique-constraint race guards for checkout, exchange, and rental settlement.

The tension

Two cashiers scan the same barcode into two carts. Exactly one checkout must win, and the loser must be told which unit and why — without a status flag, without a lock table, and without an in_cart state the spec has explicitly removed.

○

SELECT … FOR UPDATE on the unit

Works, and is application locking by another name. It also serialises the whole counter behind one row on a pooled free-tier connection.

○

Unique constraint on non-reversing sale lines

What the spec specifies — and it cannot work. See below.

●

Conditional UPDATE on units.status

One atomic statement whose WHERE names the expected status. Zero rows returned means someone else won.

The call

One unmanaged transaction per counter gesture, opened in the service — never a controller or a model hook — and nothing that is not Postgres I/O inside it. Receipts render after commit, from committed rows; a pdfkit render holding a pooled connection open is a real outage on free hosting.

Isolation stays at READ COMMITTED and there are no retry loops, because every race closes on a constraint or a compare-and-swap rather than on optimistic conflict detection.

One service owns unit movement. units.service writes the status change and its audit event together, as one function other services call with their own transaction.

AD-8AD-9AD-10AD-11AD-22
Prevents: five modules each inventing their own message for the same constraint violation. Translation is centralised and keyed on constraint name — which is why every migration must name its constraints explicitly rather than letting Sequelize generate them.
Conflict found

The spec’s chosen guard — unique on unit_id across non-reversing sale lines — makes exchange impossible. An exchange never touches the original line, so it stays non-reversing forever; a second sale of the same unit would violate the constraint and the piece could never be sold again. The compare-and-swap is also the literal reading of CAP-14’s own wording: still IN_STOCK at commit time.

04

Erasing a customer without touching history

Asked: how DPDP anonymisation coexists with never updating a completed transaction.

The tension

An administrator must be able to erase a person’s name, number, date of birth and email on request — while every past receipt still reproduces unchanged and every takings figure still reconciles. Those look contradictory only until you notice they describe different rows.

○

Delete the customer row

Breaks every foreign key from sales and bookings, and takes the shop’s own transaction history with it.

○

Tombstone and rewrite the snapshots

Satisfies erasure and destroys the ledger — this is exactly the UPDATE-a-completed-transaction the spec forbids.

●

Tier the rows, then forbid the join

Classify every table by what may be written to it after creation, and make historical reads structurally unable to see the customer row.

The call

Three mutability tiers settle it. Append-only ledger tables are INSERT-only. Bookings and agreements may be updated only to advance toward their terminal state, then freeze. Everything else — including customers — is ordinary master data. A row is “completed”, and so covered by the never-UPDATE rule, from the moment it reaches its terminal state, not from the moment it is inserted. Customer is master data, which is precisely why erasing it breaches nothing.

The number is released by setting it NULL under a partial unique index — Postgres does not collide NULLs, so a different person may later register it. Consent metadata is retained deliberately: it holds no personal data and is the proof that consent existed.

The load-bearing half is a read rule, not a write one. No receipt, sale view, agreement view, or dashboard figure may join to customers for a name or number. Those come from the snapshot columns on the transaction row. Without this, the schema looks correct and every historical receipt still silently changes the day someone is erased.

AD-5AD-18AD-24
Conflict found

The dashboard catalog computes new-versus-returning customers by matching on WhatsApp number. Erasure releases that number, so an erased customer’s history detaches — and a new person reusing the number merges with the old one’s sales. Q21 must match on customer_id, which survives erasure intact.

05

The order the tables have to arrive in

Asked: the migration sequence for the new tables.

The tension

Fifteen new tables, a Postgres extension, four views, and a permissions seeder — against a hosted database where down() is not a real option and a free tier gives no convenient restore.

The call

Twenty-one migrations plus three seeders, ordered strictly by dependency: extension first, reference data, then intake, then units as the hub, then the transaction tables, then unit_status_events last of the tables so every nullable foreign-key target already exists, then the views, then the report indexes.

btree_gist goes first and alone. If the host forbids the extension, that must fail on step one — not fifteen tables into a deploy, with the rental epic already written against a constraint that cannot be created.

Migrations are forward-only once hosted. A down() is written for local development and never run against a deployed database; a mistake in production is corrected by a new forward migration.

AD-20AD-4
Worth knowing: backend/AGENTS.md requires a soft-delete column on every table, but no existing table has one — users fakes it with a status value. The convention becomes real only on these new tables, and every partial index predicate has to carry deleted_at IS NULL or a soft-deleted booking blocks its dates forever.
06

A barcode that survives a database restore

Asked by Raviraj, against the draft: “instead of a simple counter we can combine the counter with timestamps, so even if the db dies and the counter resets the generated barcodes still be unique.”

The tension

The draft drew barcodes from a Postgres sequence. Print a sheet of labels 1001–1100, stick some on stock, then restore last night’s backup — the counter goes back to 1000 and the next sheet reissues numbers already on sarees. The draft handled this with a boot-time setval plus an operating rule: bin any printed-but-unscanned sheet. Honest, but a procedure a shop will not follow at 8pm on a Saturday.

○

Raw Unix timestamp

Already ten digits on its own — it eats the entire budget with no room for a counter. The 35 mm label caps the value at twelve digits, and Code 128 subset C needs an even count.

○

Day prefix plus a within-day counter

Four digits of days plus six of counter fits comfortably. But a restore on the same day still collides, which is the common case — you restore the backup taken this morning.

○

Second prefix plus a counter

Nine digits of seconds leaves one for the counter: ten labels a second. A single hundred-label sheet request blows straight through it.

●

Minute prefix plus a within-minute counter

Seven digits of minutes since 2026-01-01 IST, five digits of counter. Twelve digits, even, subset C intact.

The call

A restore takes far longer than a minute, so the minute the system comes back up in has never issued a label. No printed value can be reissued, whatever the sequence was rolled back to — and the loose sheet on the counter stays valid instead of being binned.

That deletes three things from the architecture: the boot setval, the post-restore discard procedure, and the reviewer finding that the old scheme quietly failed CAP-2’s “the sequence never rewinds”. The criterion is now met literally.

AD-17AD-28
The trade accepted: twelve digits puts the bar width at 0.289 mm against a phone-camera decode floor of roughly 0.25 mm — above it, with less headroom than ten digits would give. Chosen knowingly in exchange for 100,000 labels a minute. The caliper against a physical print is still the acceptance test.
Residual risk, named not hidden

The failure mode moves from restore to a backwards clock jump — an NTP correction or a host migration could repeat a minute. Far rarer than the case it replaces, and units.barcode UNIQUE stops being the primary defence and becomes a genuine last resort.

07

Who is allowed to give money back

Asked: the per-role authorisation matrix, previously deferred to the permissions seeder.

The tension

The rentals module adds five distinct counter gestures. Two of them — settling a return and cancelling a booking — decide how much of a deposit goes back across the counter. A third, an exchange, can refund a cash difference. The existing seeder already withholds sales.cancel and sales.refund from a cashier, so the shop already has a view on this; nothing carried it into the new module.

○

One coarse RENTALS.OPERATE verb

Simpler seeder. But anyone who can take a booking can also decide deposit deductions at return — the split becomes unexpressible, so the question cannot even be asked later.

○

Mirror the four SALES verbs

Symmetric with the existing constants file, but hand-over and settle collapse into CREATE and REFUND, which fits the shape of the old module rather than the actual gestures of the new one.

●

Five verbs, one per gesture

VIEW, BOOK, HANDOVER, SETTLE, CANCEL — granular enough that money-in and money-out can be held by different people.

The call

A cashier holds money-in only: create a sale, view, book and hand over a rental. Settlement, cancellation and any exchange that refunds a difference need a manager. Erasing a customer and changing shop settings are the owner’s alone. The accountant reads money and never moves a unit.

The granularity is the decision; the assignments are data. A shop that later wants cashiers settling returns edits one seeder row, not the schema.

AD-29
Prevents: the seeder being written twice, once by the rentals epic and once by an admin epic — and, more concretely, one person being able to both take money and give it back with no second signature.
Conflict found

The UX spec builds navigation on “CASHIER sees all of Counter”. Under this matrix a cashier’s Counter has no Return & settle, no cancellation and no Exchange. Because navigation renders only what the user holds, no UI rework follows — but that stated intent is now stale and must be corrected upstream.

What the review caught

The draft went through a rubric lens, an adversarial lens hunting for pairs of modules that could obey every rule and still build incompatibly, and a verification pass on every technical claim. It came back with seven critical findings, which took the spine from 20 invariants to 28. A second pass then found that only the criticals and highs had actually been applied — the mediums and lows were marked done but were not traceable in the document. All thirty-five were re-triaged one by one.

critical

The rental group had no home

Three sarees must share one receipt, and the draft used the word “group” without ever defining it. Resolved as a group_uuid on both rental tables — no header table, because the money is already per-unit.

critical

Mandated retry against a non-idempotent write

The free-tier cold-start rule told clients to retry, and nothing made checkout idempotent. A lost response would either duplicate a sale or report a committed one as a conflict. Every gesture now carries a client-generated key, stored unique.

critical

Two writers for the audit trail

One rule said units.service owned status; a diagram showed sales.service writing the event. Two epics would each write it, doubling every shrinkage figure. Now one function writes both.

critical

Overdue money appeared in no takings figure

The income view had no slot for overdue charges the shop actually collects, so Q1 could never reconcile against Q12 or the till.

critical

A cancelled booking had nowhere to record its refund

Deposit-return columns lived on the agreement, and a cancelled booking never produces one. The drawer would come up short with no row to explain it.

high

The range predicate reintroduced the timezone bug

Comparing a timestamp against a date parameter resolves it at the session zone — UTC on the host — which is the exact 5½-hour error the shop-time rule exists to prevent. Filtering now happens only on a pre-computed shop-day column.

high

A rule that cited code it did not match

The draft claimed to ratify the repo’s primary-key idiom while specifying a different one, and cited the unguarded rollback rather than the guarded one. Both corrected against the actual files.

The second pass

Thirty-five medium and low findings, each now either applied as a rule change or rejected with a written reason. Twenty-four were real gaps. These are the ones that would have cost the most.

applied

A handed-over piece that never comes back had no ending

The lifecycle offered SETTLED or CANCELLED and nothing for “the customer vanished with it”. One developer would write a returned_at for a piece that never returned — a lie in an audit trail — and another would leave the booking open forever, holding the unit’s dates in perpetuity. Now a fourth terminal state, WRITTEN_OFF, with both partial predicates updated to release the slot.

applied

Moving a wedding by a week billed the customer twice

Booking dates were frozen, so an amendment could only be cancel-and-rebook — and a cancellation leaves the rent as charged. Dates are now amendable while the booking is still OPEN, with the rent recomputed and the difference settled at the counter. The generated range column re-checks the overlap constraint by itself.

applied

Staff could mark a booked saree damaged and strand the booking

Nothing stopped a unit leaving the floor while a customer held a booking on it for next weekend. The booking stayed open, the deposit had no refund path, and the dates stayed blocked for a piece that no longer existed. The guard now refuses and names the booking, its window and the customer.

applied

Nothing fixed the case of any enum value

The repo writes ACTIVE; the draft wrote in_stock. Payment method would have been UPI in one epic and upi in another, surfacing only as a runtime constraint violation with a message that names nothing useful. Every constrained value is now UPPERCASE_SNAKE.

applied

The max-rental-period formula could divide by zero

The period cap divides by the overdue rate, and no constraint kept that column above zero — only above the daily rent, which was itself unbounded below. Plus nothing anywhere forbade a negative price. Non-negativity checks on every money column, and a strict positive on the overdue rate.

applied

The index set could not serve the only query permitted

Range filtering must use a shop-day expression; the indexes were plain b-trees on the raw timestamps, which that expression cannot use. They are now expression indexes — plus three that were simply missing, including the one the customer-matching question depends on.

applied

A walk-in took a different path through the same gesture

One developer would insert a walk-in booking straight at HANDED_OVER; another at OPEN, then advance it. The first produces a row no hand-over guard can ever reach — on the busiest path in the shop. Walk-ins now insert at OPEN and advance through the same compare-and-swap.

applied

Correcting a price typo rewrote last quarter’s profit

Unit prices were freely mutable, so fixing a typo a month after the sale left the margin figure and the per-unit ledger permanently disagreeing. Price columns now freeze the moment a unit first leaves stock.

rejected

Two findings about the barcode sequence, now moot

Both concerned the old counter: where the boot setval should live, and that the scheme quietly failed a spec criterion. The minute-prefix redesign removes the counter’s durability from the problem entirely, so neither finding has anything left to fix. Recorded rather than dropped, because both were valid when written.
