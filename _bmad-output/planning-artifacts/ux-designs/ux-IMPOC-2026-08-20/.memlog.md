- (decision) IA shape (Raviraj, verbatim intent): ONE app, not per-role apps. Top-level sections = (1) Inventory management, covering both retail and rental stock; (2) POS, covering both retail and rental; (3) Admin — picklists and sub-picklists; (4) Admin — shop expenses (rent, misc). - (decision) Form-factor (Raviraj): PHONE-FIRST for the operational surfaces — inventory management, POS (retail + rental), and recording misc shop expenses are all done on phones. The analytics dashboard is the exception: it is designed to be READ WIDE, on a tablet or laptop. One responsive app, two design centres: a handheld operating surface and a wide reading surface. Dashboard must remain reachable on a phone but is not optimised for it.
- (decision) RECEIPT DELIVERY (settles the spine's deferred item, half one): FOUR channels, all present on the same receipt surface — (a) view on screen, (b) Download PDF (saved locally by staff), (c) Send to WhatsApp using the number already on the customer record, (d) Print on paper at the counter. There IS a printer at the till. Channel is chosen per receipt at the moment of issue, not configured globally.
- (decision) RECEIPT PAPER (settles the spine's deferred item, half two): A5/A4 SHEET, not a thermal roll. The receipt is a document with a shop header, room for the rental terms block and the full deposit arithmetic. One print stylesheet at sheet proportions; the same layout is what the PDF and the WhatsApp attachment carry, so all four channels show one document.
- (decision) UI LANGUAGE: English only. No i18n layer, no bilingual labels, no localised receipt. Microcopy is written for a practised internal user (stakes: internal, one shop).
- (override) RAISED UPSTREAM, not resolved here — Raviraj asked that the receipt 'record should also be saved in db'. The architecture spine's receipt contract states a receipt is re-rendered on demand from committed rows and NEVER stored, and AD-19.2 forbids writing generated artefacts to disk. UX position: the RECORD is durable (sale/booking/agreement rows + AD-24 snapshots), and re-rendering the same sale.uuid or group_uuid reproduces the same document forever — which is what 'saved' needs to mean for a reprint. Persisting the rendered PDF BLOB would breach the spine and is a defect to raise, not to route around (SPEC constraint). EXPERIENCE.md specifies a durable, re-openable receipt reference; it does not specify a stored file.
- (decision) VISUAL DIRECTION: 'Warm retail'. IMPOC should carry something of a clothing shop rather than a warehouse — warm neutrals, a jewel accent, softer corners, more generous type. It belongs to SHREE Fashion Store. No existing brand assets to inherit; palette is built from this direction.
- (decision) THEME: light AND dark, both fully specified, following the device setting (prefers-color-scheme). Staff phones vary. No in-app toggle required beyond respecting the OS.
- (decision) SCAN CADENCE (Raviraj, the single biggest behavioural fork — settled explicitly): SCAN-CONFIRM-SAVE-REARM, camera off between units. The camera starts ONLY to scan a barcode. On a successful decode the camera TURNS OFF immediately. The user then enters colour and size on a still screen. A Save button writes the unit into inventory. A separate 'Add another unit' button re-arms the camera and the cycle repeats. There is NO rapid-fire mode and NO live camera between units. Consequences: the 'N of M scanned' counter increments on SAVE, not on decode; the camera is never running while a form is being typed into; a decode never commits anything on its own.
- (decision) DASHBOARD SHAPE: owner-configurable cards. The owner pins the questions they care about to the top; the remaining questions live in a browsable library. Every card is still an AD-14 summary/drill pair — pinning changes what is on screen, never what a figure means.
- (assumption) [ASSUMPTION] The owner's pinned-card set has no table in the architecture spine (no dashboard_preferences entity; app_settings per AD-28 is shop-wide admin tuning, not per-user layout). UX therefore specifies the pinned set as CLIENT-SIDE persistence keyed by user, same tier as the AD-25 cart. Server-side persistence across devices would need a new table and is an upstream change to raise, not to assume.
