# IMPOC Versioning & Releases

**Document for every agent on this floor.** Read this before touching version numbers,
tags, or releases. The orchestrator (god) owns the actual bump + tag at integration
time; workers propose, god disposes.

## One rule to remember

> Every change that ships to the shop laptop gets a **SemVer bump** (`MAJOR.MINOR.PATCH`)
> and an **annotated git tag** (`vX.Y.Z`) on `main`. GitHub **Releases** are created only
> **occasionally**, when there is a **major improvement** worth shouting about.

Semantic versioning spec: https://semver.org. Version shape is always `X.Y.Z` — no `v`
inside `package.json`, `v` only on the tag.

From this baseline the next bug fix becomes **1.0.1**, the next feature **1.1.0**, the
next breaking change **2.0.0**.

## Bump matrix — how big is the change?

Bump by the **impact and size** of the change, not just its type.

### PATCH — `1.0.0 → 1.0.1` (bug fix / tiny)
- Bug fixes (a broken flow that now works).
- Small UI/text/validation fixes with no new behavior.
- Performance/security tweaks that change no interface.
- Reverts, small CSS, wording, seed-data text corrections.
- **Empty catch-all?** No — a sloppy fix that silently changes behavior is a PATCH only if
  the behavior is what was always *meant*; anything that changes a workflow contract is a MINOR.

### MINOR — `1.0.0 → 1.1.0` (feature / enhancement, backwards-compatible)
- Any new feature, screen, module, or API route.
- New field/column with a default (non-breaking), new picklist option, new report.
- Any R-series feature ticket that lands → MINOR (`+1` on the minor digit).
- Old data, old calls, and old UI keep working after the change.

### MAJOR — `1.0.0 → 2.0.0` (breaking / big change)
- **Breaking API or contract**: renamed/deleted routes, changed request/response shapes,
  auth or permission semantics changes.
- **Destructive migration**: a migration that drops/rewrites data or columns in a way that
  old code can't read anymore.
- **Feature removal** (e.g. if R-52 ever ends in *Remove templates*).
- **Platform/size overhaul**: React/node/library major upgrades, a full-screen workflow
  rework (like the POS rework), anything that changes how the staff *uses* the app day to day.
- Two or more MINOR-scale features that land together and together change the feel of the app.

### Unsure?
- Default to MINOR.
- Mixed change (fix + feature in one release): the release gets the **highest** bump of its
  parts. Better: split so each bump stays honest.
- A worker should propose its bump level in the done report; **god decides** at integration.

## Where the version lives

Two tracked places must always show the **same** number:
1. `backend/package.json` → `version`
2. `frontend/package.json` → `version`

(`package-lock.json` files are **gitignored** in this repo — they are regenerated by
`npm install` and carry the version locally only; you can ignore them for tagging.)

Tags (`vX.Y.Z`) are the **historical record**; the `package.json` pair is the **current value**.

## Tagging workflow (god, at integration time)

Runs for every change that lands on `main`:

1. Confirm `main` is fetched/up to date and the feature's code is merged on **both**
   `main` and `context` (app code ships to both — R-64/R-65/R-66 convention).
2. Decide the bump (`1.2.3` per the matrix above).
3. On `main`, edit the version pair (`backend/package.json` + `frontend/package.json`) to `1.2.3` (no `v`).
4. Commit: `build: v1.2.3 — <ticket id> <short summary>`
5. Tag the **commit** (annotated):
   ```bash
   git tag -a v1.2.3 -m "<ticket id> — <short summary>"
   ```
6. Push **branch + tag**:
   ```bash
   git push origin main --tags
   ```
7. Sync `context` (it carries the same code + docs; cherry-pick the version commit).
8. Record the version on the ticket card in `context/tasks.json` + `hive/tasks.json`
   (in `details`), and note it in `context/board.md` + `CONTEXT.md`.

**Only god tags.** Workers never bump versions or tag — a merged tag later than the version
they edited just adds noise.

**Docs-only changes** (`CONTEXT.md`, `board.md`, `tasks.json`, `VERSIONING.md` itself, hive
files) get **no bump and no tag** — they never reach the laptop as code.

## GitHub Releases (occasional, user-driven)

- Create a **GitHub Release** only for a **major improvement**:
  - a new **MAJOR** version, **or**
  - a milestone where several notable improvements/discoveries accumulate (a user call).
- One release per tag. From the tag `vX.Y.Z`, title `vX.Y.Z`.
- Release notes: list the shipped tickets + 2–5 bullet "what changed" lines written for the
  shop owner (features and fixes in plain language, not ticket jargon).
- `gh` is installed (`/opt/homebrew/bin/gh`, 2026-09-18). The macOS-keychain token works for
  repo-scoped `gh` commands through `GH_TOKEN` (it lacks `read:org`, so interactive
  `gh auth login` won't validate — but releases/PRs/issues on this repo are fine):

  ```bash
  GH_TOKEN="$(security find-internet-password -s github.com -w)" \
     gh release create v1.2.3 --title v1.2.3 --notes-file /tmp/release-notes.md
  ```

  Never echo the token; `unset GH_TOKEN` right after. (Optional, interactive: `gh auth login`
  once via the device flow to mint a fresh full-scope token and drop the `GH_TOKEN=` prefix.)
- Or draft it in the GitHub web UI. God drafts; the user publishes / decides timing.

## FAQ

- **Do we bump for every tiny hotfix?** Yes — that's the whole point of PATCH. The shop
  laptop pulls `main`, so the version it runs on is always verifiable from a tag.
- **Pre-1.0?** No — the app is in production, we start at `1.0.0` (baseline above). If a
  staged rollout is ever needed, pre-release suffixes (`1.1.0-beta.1`) may be used.
